# Modules v3 and checks v3 discussion record

## Purpose and reading order

This document preserves the complete substantive design discussion in this chat: the
original idea, every question and answer, concrete examples, proposals, corrections,
decisions, and remaining implementation choices. It also records the documentation and
pull-request handling discussed afterward.

Read the rounds chronologically. Earlier answers are historical when a later answer
changes them. In particular, the proposals for mandatory module roles/types and errors
on selecting a NixOS-only module from Home Manager were superseded. They are retained here
so the reasoning and the user's corrections are not lost.

Speaker labels distinguish user decisions from assistant proposals. A question does not
become an accepted requirement merely because it appears here. Questions with brief answers
retain both the question and its answer so their meaning remains clear.

This is a discussion record, not a new implementation specification or validation report.
[MIGRATION.md](MIGRATION.md) tracks the migration contract and implementation status.
[lib/modules/README.md](lib/modules/README.md) documents the implemented constructor API.
Those files have since evolved on the task branch; this record does not claim that their
later implementation details were all decided in this conversation.

## Original proposal

The user described the idea as very rough, said that a dedicated modules-v3 branch already
existed, and asked for questions before formalizing the design in `MIGRATION.md` or a
similar document once both parties were happy.

### mkModule inputs

- IDs, as a list.
- A Nix function including everything it needs, with Home Manager inline.
- A check declaration.
- A package declaration.
- Arguments such as username and hostname, derived from the importing host.
- Imperative steps and other module documentation, as text.

### mkModule outputs

- A NixOS module containing its package and the imperative steps as documentation.
- A Home Manager module.
- A package.
- A check mapped to that file in GitHub Actions.

### mkHost inputs

- IDs wired to the IDs in `mkModule`.
- A role: Home Manager versus normal/NixOS.
- Arguments.

### mkHost output

- A host.

## Initial repository context

The assistant inspected the existing configuration before asking questions. At that time,
the working tree was clean on `refactor/modules-v3`. The current system embedded Home
Manager in system modules, with packages, checks, and CI wiring elsewhere. Flake-parts and
import-tree provided the existing import structure.

The assistant's initial reading was to bring those pieces into one declaration. That was
a proposed interpretation, not yet an agreed API.

## Round 1: IDs, host role, and the configuration function

### 1. Meaning of IDs

**Assistant question:** Are IDs tags selecting groups, such as a browser declaring
`["desktop" "browser"]` and a host requesting `"desktop"` receiving every matching module?
Or are they unique module names/dependencies?

**User answer:** “Ids are for dependency management and importing. If a host has all the
modules a module has, it should import it.”

The later rounds clarify this wording into an all-IDs selection rule, without dependency
resolution.

### 2. Meaning of the host role

**Assistant question:** Should `mkHost` produce either a NixOS configuration with Home
Manager integrated or standalone Home Manager, for example on another distribution? For
standalone Home Manager, should a module's system settings be skipped or rejected?

**User answer:** `mkHost` can produce either Home Manager or NixOS configuration. The
NixOS module generated by `mkModule` contains Home Manager inline, as in the existing
configuration.

### 3. One function and two sections

**Assistant question:** Would explicit sections in one function, roughly
`{ nixos = …; home = …; }`, fit, alongside optional package, check, and documentation
declarations? Each section would have its own configuration context, with everything in
one file.

**User answer:** Yes.

**Assistant preference:** Explicit system/home sections and optional package/check
declarations, since locale or SSH configuration might have no package of its own.

**User feedback:** “I'm not happy. I want the concept to be more concrete.”

## Round 2: Concrete proposed contract

The assistant proposed that a host supplies IDs and a module matches only when all its
IDs occur in the host's set. The example host was:

```nix
mkHost {
  role = "nixos";
  ids = ["base" "desktop" "gaming"];

  args = {
    hostName = "armin";
    userName = "nixi";
    system = "x86_64-linux";
  };
}
```

This historical example is superseded in two details: `hostName` is derived from the host
name, and `system` is a dedicated `mkHost` field rather than a host argument.

The selection example was:

| Module | Required IDs | Selected |
| --- | --- | --- |
| shell | `["base"]` | Yes |
| browser | `["desktop"]` | Yes |
| gaming | `["desktop" "gaming"]` | Yes |
| server | `["base" "server"]` | No |

The assistant distinguished a module's name, identifying exports, from its IDs, describing
selection requirements, and proposed this illustrative declaration:

```nix
mkModule {
  name = "example";
  ids = ["desktop"];

  module = {pkgs, args, package, ...}: {
    nixos = {
      # System settings, including services and persistence.
    };

    home = {
      home.packages = [package];
      # Home Manager settings.
    };
  };

  package = {pkgs, ...}:
    pkgs.callPackage ./package.nix {};

  check = {pkgs, nixosModule, homeModule, ...}:
    # A check that exercises the generated module.
    ...;

  docs = ''
    Configuration and usage information.

    After first installation:
    1. Perform the required manual setup.
  '';
}
```

This was schematic, not runnable code or an approved final signature. Singular `package`
and `check`, combined documentation/steps, and attrset sections were refined afterward.

The assistant proposed these behaviors:

- Register module exports independently of host selection.
- Expose a named NixOS module, Home Manager module, and any per-system package/check.
- Wrap `nixos` and `home` in the NixOS export, placing home configuration under
  `home-manager.users.${args.userName}`.
- Apply only `home` for the Home Manager export.
- Have `mkHost` select registered modules and supply shared arguments.
- Make package/check declarations optional.
- Exporting a package does not itself determine installation.
- Keep docs with the module and show them in generated documentation.
- Keep manual steps as user instructions.
- Carry the declaring file path into CI metadata for checks.

**Assistant question:** With host IDs `["gaming"]` and module IDs `["desktop" "gaming"]`,
should selection exclude the module or automatically bring in desktop support?

**User corrections and decisions:**

1. Multiple packages can be defined in one module.
2. Multiple checks can be defined in one module.
3. No automatic desktop support. “ids are dumb.” The only ID rule is that a host imports a
   module when it has all that module's IDs.
4. There must be a way to install packages in NixOS rather than Home Manager.

**User process instruction:** “More questions please. Even for obvious things. I want to
be in full control of the refactor.”

## Round 3: Identity, discovery, installation, and host configuration

### 1. Module identity

**Assistant question:** Explicit unique name, or derive it from the file path? Suggested
an explicit name and rejection of duplicates.

**User answer:** Explicit name.

### 2. File boundaries

**Assistant question:** Multiple `mkModule` declarations per file, or exactly one?
Suggested allowing multiple.

**User answer:** Multiple modules allowed, but discouraged.

### 3. Discovery

**Assistant question:** Automatic discovery under a designated directory, like current
recursive imports, or an explicit registry listing files?

**User answer:** Automatic discovery.

### 4. Empty and omitted IDs

**Assistant question:** Should `ids = []` match every host, and should omitted IDs also
default to `[]` rather than fail?

**User answer:** Agreed to both.

### 5. Selection overrides

**Assistant question:** Explicit host includes/excludes, or IDs exclusively? Noted that
exclusive selection means exceptions need different IDs or split modules.

**User answer:** IDs exclusively. No limit on the number of IDs.

### 6. Package installation

**Assistant question:** Explicit installation in sections, such as the following, or
installation shorthand fields?

```nix
nixos.environment.systemPackages = [packages.example];
home.home.packages = [packages.other];
```

**User answer:** Explicit looks okay.

### 7. Export names and collisions

**Assistant question:** Global package/check names or names prefixed by the declaring
module? What happens on collision? Suggested rejecting collisions.

**User answer:** Prefix by the module name. A module's default package has the module's
name. Reject collisions.

### 8. System-only module on Home Manager

**Assistant question:** When a selected module has only a NixOS section, should standalone
Home Manager silently get nothing, warn, or fail? Suggested explicit supported-role
declarations and an error.

**User answer at this stage:** Error.

**Later correction:** Silently do nothing; no module types/roles declaration. See round 6.

### 9. Requested host arguments

**Assistant question:** Receive the entire host argument set or declare requested
arguments? Missing values fail on use or validate declarations? Suggested explicit
requirements for useful errors.

**User answer:** Declare the arguments to receive, then use them in the module. Arguments
can have defaults if possible in Nix.

### 10. Host-specific settings

**Assistant question:** Where do settings such as Armin's wallpaper dimensions belong:
host arguments, local configuration, or ordinary `custom.*` options? Retain `custom.*`?

**User answer:** Arguments.

### 11. Additional user requirement

**User:** `mkModule` should also have an optional assertions section.

## Round 4: Argument declarations, contexts, roles, and assertions

The assistant noted that Nix supports defaults such as `{userName, port ? 8080}: …`.

### 1. Missing arguments and selection

**Assistant question:** Fail for a missing required argument only when a host selects the
module, so unrelated modules do not impose irrelevant settings?

**User answer:** Yes.

### 2. Argument declaration format

**Assistant question:** Typed declarations with descriptions and defaults, or function
parameters alone? Proposed:

```nix
args.port = {
  type = lib.types.port;
  default = 8080;
  description = "Port used by the service.";
};
```

**User answer:** Common arguments are defined separately from `mkModule`; module-specific
arguments are simple function parameters. The proposed declaration concept is good.

### 3. Argument visibility

**Assistant question:** Receive only declared host arguments, separately from normal
evaluation arguments such as `pkgs`, `lib`, and `config`?

**User answer:** Yes.

### 4. Shared versus module-specific names

**Assistant question:** If two modules declare `port`, does one host value configure both,
or should names be namespaced? Support both shared and module-specific arguments?

**User answer:** Unrelated modules should not use the same name in the first place. Use
`port-module1` and `port-module2`. Distinguish arguments used across modules, such as
`userName`, from arguments used by one module.

### 5. Section contexts

**Assistant question:** Separate section functions with their own `config`, while host
arguments and packages can be captured by the enclosing function?

```nix
nixos = {config, lib, pkgs, ...}: { /* ... */ };
home = {config, lib, pkgs, ...}: { /* ... */ };
```

**User answer:** Yes.

### 6. Supported-role declarations

**Assistant question:** Infer support from sections or explicitly declare it? Suggested
that home-only modules could support both hosts via embedding, while NixOS-only modules
would fail on Home Manager.

**User answer at this stage:** Explicitly declared. A Home Manager host importing a module
with both sections uses only its home section. There is no NixOS-only host concept: all
NixOS hosts have inline Home Manager, as in the current configuration.

**Later correction:** Remove module type declarations entirely; retain the host behavior.

### 7. Assertion format and scope

**Assistant question:** Assertions about arguments, evaluated system/home settings, or
both? Use the vanilla assertion/message shape?

```nix
assertions = [
  {
    assertion = /* condition */;
    message = "Explanation of the requirement.";
  }
];
```

**User answer:** Vanilla NixOS assertions. This is okay.

### 8. Check values

**Assistant question:** Explicit fixtures or run checks per matching real host with its
arguments? Suggested explicit fixtures, with actual-host tests when needed.

**User answer:** Explicit fixtures.

### 9. Cross-module package consumption

**Assistant question:** Can a module consume another module's packages? Must the owner
also match the host, or are all registered packages available?

**User answer:** No. If something needs to be done with a package created by a module,
that module should do it. If closely related to another module's functions, the modules
should depend on each other.

Later discussion clarifies that this relationship uses IDs, not a separate dependency API.

### 10. Default check naming

**Assistant question:** Should a check named `default` export as the module name, matching
the default-package convention?

**User answer:** Yes.

### 11. Host escape hatch

**Assistant question:** Can `mkHost` accept ordinary local configuration for hardware,
disks, and one-offs, or must everything use discovered `mkModule` declarations?

**User answer:** No escape hatch. Everything goes through `mkModule`.

### 12. Users

**Assistant question:** One Home Manager user per NixOS host, or several users with
different IDs and arguments?

**User answer:** One Home Manager user only.

**User request:** More questions.

## Round 5: Relationships, defaults, architecture, and documentation

### 1. Separate dependency declaration

**Assistant question:** Should `requires = ["other-module"]` fail unless the other module
also matches, validating dependencies without auto-import?

**User answer:** Modules depend based on IDs. If gaming has `["gaming" "desktop"]`, it
depends on all modules having just `["desktop"]`.

### 2. Dependency cycles

**Assistant question:** Allow mutual dependencies when both modules are selected, or
reject cycles?

**User answer:** Addressed by answer 1.

### 3. Dependency access

**Assistant question:** Does a dependency just ensure presence, with ordinary option
interaction, or expose additional things?

**User answer:** Addressed by answer 1.

### 4. Roles renamed to types

**Assistant question:** Would `roles = ["nixos" "homeManager"]` work, and should it be
mandatory? Home Manager would evaluate only `home`, NixOS both available sections.

**User answer at this stage:** Rename roles to types; types are mandatory. “We don't use
home manager standalone for nixos modules.”

**Later correction:** `mkModule` has no types section. See round 6.

### 5. Home-only modules

**Assistant question:** Can a module support both host roles while containing only `home`?

**User answer:** If a module has only a home section, generate a NixOS module automatically.

### 6. Shared argument documentation

**Assistant question:** Typed common declarations with descriptions, optional defaults,
and automatically generated argument documentation?

**User answer:** Yes.

### 7. Derived host values

**Assistant question:** Explicit `hostName`, `userName`, and `system`, or derive some from
the host name or other declaration fields?

**User answer:** Derive hostname from the host name. All others explicit.

### 8. Host argument set and diagnostics

**Assistant question:** One host argument set like this? Unknown or unused names fail,
warn, or pass? Suggested failing on unknown names.

```nix
args = {
  userName = "nixi";
  port-module1 = 8080;
  port-module2 = 9090;
};
```

**User answer:** Yes. Unknown host arguments fail; unused arguments warn.

### 9. Shared enclosing parameters

**Assistant question:** Declare module-specific parameters once on the enclosing function
and capture them in both sections?

```nix
module = {userName, port-example ? 8080}: {
  nixos = {config, pkgs, ...}: { /* ... */ };
  home = {config, pkgs, ...}: { /* ... */ };
};
```

**User answer:** Looks okay.

### 10. Host-dependent exports

**Assistant question:** Can packages/checks request host arguments, or must exports be
host-independent? Host-dependent exports would need names for differing host values.

**User answer:** Packages/checks have their own values to avoid package clutter. If a
package needs host values, define it as a lambda.

### 11. Assertions for Home Manager

**Assistant question:** Apply shared assertions to standalone Home Manager too, with
section-local assertions for conditions using the respective `config`?

**User answer:** Yes; an assertion can always be conditional with `mkIf`.

### 12. Removing custom options

**Assistant question:** Eliminate repository-defined `custom.*` options in favor of
arguments while retaining upstream options, or allow module-defined options for others?

**User answer:** Yes, replace `custom.*` with arguments.

### 13. Supported architectures

**Assistant question:** Supported-system declarations for modules/packages/checks, with
failure if a selected module does not support the host architecture?

**User answer:** Keep flake-parts for x86 and aarch64 support for all checks and packages.
Modules do not use a supported-systems mechanism; they are independent of the host system.

### 14. Documentation output

**Assistant question:** A generated page listing IDs, roles, arguments, dependencies,
packages, checks, and freeform instructions, with host pages listing selections and steps?

**User answer:** Documentation is a desktop entry launching static-site-generated HTML in
the browser, using Zensical or another generator. One page per `mkModule`, roughly:

```markdown
# MODULE NAME

## Module docs

## Imperative steps
```

Also generate one page with all imperative steps, grouped under module-name headings.
The original answer ended after the proposed `# MODULE NAME` heading for that page.

**Assistant question:** What type values should exist? Both versus NixOS-only support?
Home-only sections would still get an inline NixOS wrapper.

**User correction:** `mkModule` does not have a types section. If a NixOS-only module,
meaning one without a Home Manager section, is imported by a Home Manager configuration,
it silently does nothing.

### 2. Type mismatch handling

**Assistant question:** Error on an ID match with unsupported type, or filter by type?

**User answer:** See answer 1. This supersedes the earlier error decision.

### 3. Meaning of subset relationships

**Assistant question:** Are modules with `["gaming"]`, `["desktop"]`, and `[]` all
dependencies of a module with `["gaming" "desktop"]`, since they are always selected too?

**User correction:** These are not all dependencies, but modules that must be imported
along with it.

### 4. Equal ID sets

**Assistant question:** Two modules with `["desktop"]` always appear together, without
ordering or dependency distinction. Is that intentional?

**User answer:** Yes.

### 5. Host name spelling and declaration layout

**Assistant question:** Use `hostName`, matching existing conventions? Use a host attrset
key such as `hosts.armin = mkHost { ... };` to supply its name?

**User answer:** `hostName` is fine. “whatever” on the layout.

### 6. Required common arguments

**Assistant question:** Required for every host merely because declared, or only when a
selected module requests them? Suggested the latter, except construction essentials.

**User answer:** The latter.

### 7. Default precedence

**Assistant question:** Can module parameters override common defaults, with precedence

**User answer:** Exactly, but this generally should not happen.

### 8. Package lambdas

**Assistant question:** Where should host-dependent factories live? Ordinary flake package

**User answer:** Inline in the module, in a `let … in` block.

### 9. Section access to packages

**Assistant question:** Should both section functions receive their module's own packages
and package factories? Illustrated explicit `environment.systemPackages` installation.

**User answer:** Yes, sections should receive packages.

### 10. File mapping and CI

**Assistant question:** Does changing a module file run all checks declared there? Do

**User answer:** Yes to all three. Check how checks v2 works.

### 11. Documentation scope

**Assistant question:** All registered modules or only modules selected on that host?
Same scope for combined imperative steps?

**User answer:** Only modules present on the host.

### 12. Generator and local HTML

**Assistant question:** Build HTML with the configuration and open it locally through a

**User answer:** Yes. Likes Zensical, but the assistant may choose what fits.

### 13. Text or functions

**Assistant question:** Plain Markdown or functions of declared arguments, for example

**User answer:** Docs can contain arguments, though it probably will not be needed.
Imperative steps are a separate input from general docs.

### 14. Terminal hosts

**Assistant question:** Always provide documentation as a package/output, with graphical

## Checks v2 inspection

Before the final round, the assistant inspected the existing check workflows, check
declarations, documentation, mapping, and selection logic, including:

- `.github/workflows/flake-build.yaml`.
- `.github/workflows/build-targets.yaml`.
- `.github/workflows/regression-checks.yaml`.
- `.github/workflows/flake-check.yaml`.

- `github-actions/default.nix` and `docs/checks.md`.
- An existing upgrade-service behavioral/regression fixture and `zensical.toml`.

The relevant observed checks-v2 behavior was:

- Basic validation runs independently of changed-file behavioral selection.
- Every exported non-ISO package builds on every PR, on its supported systems.
- Behavioral checks use a manually maintained file-to-check map.
- Shared infrastructure changes select the complete non-ISO check suite.
- Unclassified configuration changes fall back to the entire behavioral suite.
- The diff is against the merge base, with NUL-delimited filenames and rename detection
  disabled to preserve both old and new paths.
- Matrix and mapping agreement, duplicate targets, and target attributes are validated.
- VM checks run on x86; portable package and documentation outputs cover both systems.
- ISO builds/smoke tests have a separate tier.
- Scheduled/manual full runs include host builds and the complete applicable suite.
- Regression-proof runs build positive and deliberately broken controls.
- `all-systems-passed` is the stable aggregate status and validates expected skips.
- Selection summaries, caches, and retained failure logs support diagnosis.

These observations supplied context for the next questions. They do not mean the user
accepted every old policy unchanged.

## Later repository guidance supplied in this chat

The user subsequently replaced the original AGENTS.md instructions with modules-v3 guidance.
This is repository operating context, rather than another question-and-answer design round.
It describes a repository whose implementation has progressed since the original discussion:

- `lib/modules/` implements discovery, constructors, argument binding, and fixtures.
- `modules/<name>/` owns declarations, packages, checks, docs, and companion sources.
- `modules/host-<name>/` holds host-specific configuration.
- `hosts/*.nix` holds discovered hosts; `arguments/` holds shared typed declarations.
- Regular `.nix` files are recursively discovered; underscore-prefixed sources and
  fixtures are excluded.
- Host declarations contain only `name`, `role`, `system`, `ids`, and `args`.
- Shared context is explicitly requested. Sections keep their respective configuration
  contexts, and shared home sections avoid requiring `osConfig`.
- Generated NixOS modules own inline integration for one home user.
- Packages/checks use owner prefixes and default-name expansion; installation is explicit.
- Common-argument docs are generated with `nix run .#module-docs-update`, with the freshness
  check at `.#checks.x86_64-linux.module-docs`.
- Nix validation evaluates both systems; VM execution and builds are distinct validation.
- Existing state versions, preservation guards, encrypted secrets, and focused changes
  remain required. `docs/usage.md` needs an explicit request before editing.

The general repository instructions still describe task branches, conventional commits,
validation, pushes, and PRs. The user's specific “Don't PR yet” instruction and the explicit
promise above remain the applicable exception for this work.

## Final decision checklist

This checklist restates the final decisions without the superseded alternatives. Checked
items mean discussed and agreed, not implemented or tested by this document change.

- [x] `mkModule` has an explicit unique name; reject name collisions.
- [x] Allow multiple declarations per file, but discourage them.
- [x] Give each module its own directory and discover automatically.
- [x] Separate discovery roots for modules, hosts, and common arguments; underscore excludes.
- [x] Select solely by all module IDs being present in host IDs.
- [x] Omitted or empty module IDs match every host.
- [x] No ID limit, dependency resolver, automatic support import, or include/exclude override.
- [x] Equal ID sets mean modules are selected together, without an implied order.
- [x] `mkHost` produces NixOS or standalone Home Manager; `system` is a dedicated field.
- [x] Derive `hostName` from the host name; other settings are explicit or use declared defaults.
- [x] No module `types`/`roles` field; section presence determines applicable configuration.
- [x] Home Manager hosts ignore NixOS-only configuration and its inactive requirements.
- [x] A home-only declaration gets an automatically generated NixOS wrapper.

## Alternatives explicitly superseded or declined

- Matching any one ID rather than all IDs.
- Resolving dependencies or automatically adding desktop support for gaming.
- A separate `requires` graph, cycle policy, or dependency-access interface.
- Host includes/excludes bypassing IDs.
- Mandatory module roles/types and failures for Home Manager selecting NixOS-only modules.
- Deriving module identity solely from file paths.
- Requiring exactly one declaration per file.
- Explicit file registries replacing automatic discovery.
- Installing declared packages implicitly or only through Home Manager.
- Global unprefixed export naming or accepting collisions.
- Giving every module every host argument automatically.
- Reusing unrelated settings under ambiguous names such as a shared `port`.
- Keeping `custom.*` as the host-specific configuration mechanism.
- Requiring every common argument on every host regardless of selection.
- Exporting a package per host or adding a public package-factory namespace.
- Letting modules use other modules' package exports.
- Borrowing production-host values implicitly for checks.
- Putting Home Manager integration in `mkHost`.
- Inline arbitrary host configuration or module-import escape hatches.
- Multiple Home Manager users on a NixOS host.
- Running KVM checks on aarch64.
- Keeping all-package PR builds from checks v2.
- Falling back to all behavioral tests when a changed module has none.
- Making docs opt-in, showing all registry modules, or having `open-docs` choose GUI mode.
- Requiring empty-doc placeholders or an imperative-step dependency/order engine.
- A supported gradual production-host migration with v2 and v3 coexistence.

## Details not fixed by the design discussion

The discussion did not choose every exact field spelling, directory path, binding
implementation, terminal-browser package, documentation theme, or source layout. The user
delegated generator suitability and did not insist on a host attrset layout.

Examples such as `watchPaths`, `homeManager`, `homeManagerModules`, singular `package` and
`check`, and the early location of `system` were proposals, not all final API spellings.
Consult the current constructor README for the implemented choices rather than copying
historical snippets as executable configuration.

The assistant's migration plan also carried forward repository validation and CI safeguards:
preserve behavior and state versions, retain full/ISO/regression tiers and useful failure
diagnostics, test discovery/arguments/selection, handle renamed/deleted ownership, and keep
deployment separate. These were formalization and existing-policy context; they were not
additional numbered user answers in the rounds above.

The original discussion did not itself establish the success of subsequent implementation
tests. No implementation status checkbox in this record should be inferred from agreement
on a design decision. Use the current migration status and actual validation evidence for
that purpose.
